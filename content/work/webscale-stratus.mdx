## Overview

Stratus MaaS was MageMojo's control panel for Magento hosting, and <mark>three very different people needed the same screen to work for them.</mark> A store owner wanted reassurance that the site was up. A developer wanted root-level control. A support agent needed to answer both without becoming a translator between them.

Most competitors solved this by picking a side: friendly for beginners, or powerful for developers. That compromise was costing MageMojo about 80 support tickets a month and a slow bleed of technical customers who outgrew the tool.

I led the research, information architecture, visual system, and testing behind a single panel built to serve all three at once.

## The Problem

The panel wasn't broken for anyone who already understood it. The cost showed up in the numbers around it:

- **~80 support tickets a month** traced to configuration confusion (DNS, SSL, deployment settings)
- **20+ minutes per ticket** spent re-explaining features that should have explained themselves
- **Technical users churning** within 6-12 months, outgrowing a beginner-simplified interface with no deeper layer to grow into

> Left alone, MageMojo would keep losing exactly the higher-revenue technical accounts it most needed to retain, not because the hosting was bad, but because the interface forced a choice nobody should have had to make.

## Initial Understanding

The obvious framing was simplicity versus power, the same tradeoff every competitor had already accepted. Whether a third option existed was the open question.

I didn't know what store owners wanted beyond "less confusing," whether developers would tolerate a friendlier surface, or whether support staff faced the same confusion as customers. <mark>The hard constraint: it had to ship as one interface.</mark> No segmented modes, no separate logins per user type.

## Discovery & Learning

Five interviews across the real user base: two store owners (~$500K/year and $10M+/year), one CTO, two support agents. A small sample, and I'll come back to that, but it surfaced the finding that reshaped the project.

**Store owners don't think in infrastructure.** Logging in, they have one question: is my site working? DNS, SSL, and server config are all secondary to that.

The surprise: this wasn't unique to store owners. <mark>The CTO and support agents also wanted "is everything healthy" answered first.</mark> The difference was tolerance for depth after that, not the existence of the question itself.

## Defining the Real Problem

This was never simplicity versus power. It was sequencing. Every user wanted the same first answer and diverged only on how much came after it, and how fast.

> That reframed the brief: build around the real order people needed information in, status, then action, then configuration detail, so a first-time store owner and a CTO could use the identical screen without either feeling like it was built for someone else.

## Exploring Solutions

Three concepts, sketched and evaluated against real user behavior before committing to one:

**Guided wizard.** Simple to follow, but rigid. Developers and any store owner with a non-standard setup would need to deviate from the happy path, and a wizard has no good answer for deviation.

**Everything visible at once.** Full transparency, close to what already existed. It's what developers said they wanted when asked directly, but it recreates the exact overwhelm the project was meant to fix.

**Layered disclosure.** Status-first, expanding into full technical depth on demand. Selected, but conditionally: <mark>it only works if the layers follow the sequence users actually follow, not a basic-versus-advanced guess made at a desk.</mark>

## Design Decisions

Four decisions carried the redesign.

### 1. Sequence around "is it working," not the feature list

**Problem:** Three user types, three depths of information, one shared screen.

**Alternatives:** Guided wizard (too rigid outside the happy path). Everything visible (overwhelmed non-technical users).

**Why this approach:** The divergence was about speed to the first answer, not the ceiling of what people wanted access to. Status → action → configuration gave everyone an immediate answer and room to go deeper.

> **Impact:** Resolved most usability complaints in round-one testing. Store owners confirmed, unprompted, that status came before configuration.

### 2. Organize labels around intent, not system architecture

**Problem:** The real structure was technical (DNS, SSL, Nginx, autoscaling). Store owners don't reason in those terms; flattening the vocabulary risked frustrating developers who needed precision.

**Alternatives:** Keep the existing technical vocabulary as-is. Matches the infrastructure, but testing showed users didn't know what "Docroot" or "Instance Type" meant without context.

**Why this approach:** Sections named around intent ("Configure Domain," not "DNS Management"), with a one-sentence plain-language explanation on every technical option. Developers kept precise terms; everyone else got a way in.

> **Impact:** Contextual help was one of the highest-leverage single changes in testing, targeting the exact failure mode behind most support tickets.

### 3. Build a component system where color and type carry meaning

**Problem:** 25+ screens needed to communicate health and technical precision at a glance, without a legend or a separate technical mode.

**Alternatives:** A neutral system relying on text labels alone. Lower design overhead, but it puts the burden of parsing status on reading instead of scanning.

**Why this approach:** A semantic color system (blue for healthy/primary, orange for warnings, red for errors), plus a monospace typeface reserved for technical content, signaling precision without a separate screen. 30+ components documented against this system.

> **Impact:** Developers described the shipped product as showing "everything without clutter." Support staff described it as eliminating a knowledge silo.

### 4. Progressive disclosure instead of a separate advanced mode

**Problem:** Developers needed fast, full access to advanced settings like autoscaling and server config.

**Alternatives:** A distinct developer mode, functionally a second product. Ruled out for fragmenting the interface and reintroducing the simplicity-versus-power tradeoff.

**Why this approach:** Advanced settings collapsed by default, expandable in place, inside the same navigation a store owner used.

> **Impact:** Developers and support staff both reached 100% adoption, on the same interface, no separate mode required.

## Iteration

Four rounds of testing, each driving a structural change:

- **Round 1** (3 users, wireframes): confirmed store owners lead with "is everything okay." Dashboard restructured around status.
- **Round 2** (4 users, visual + copy): "Docroot" and "Instance Type" weren't self-explanatory. Contextual help added throughout.
- **Rounds 3-4** (full review): advanced settings consolidated, change history added, ambiguous icons clarified.

The clearest before-and-after is the URLs List page: scattered status and unclear validation states, replaced by color-coded indicators and organized columns for domain, status, SSL, DNS, and file validation.

## Reflection

The biggest lesson: <mark>a multi-persona problem is sometimes a sequencing problem in disguise.</mark> I started out framing this as simplicity versus power, the same frame every competitor had accepted. The three groups weren't actually divided on what they wanted, only on how much of it they wanted immediately versus later.

The second lesson: explaining jargon and removing jargon are different fixes. Keeping precise terms in place while adding plain-language context served both audiences better than simplifying the vocabulary would have.

If I ran this again, I'd want a larger interview base before committing an entire information architecture to a pattern from five conversations. It held up here, through four rounds of testing and the numbers after launch, but it's a thin evidence base for a decision this structural.

> The three user types weren't disagreeing about what they wanted first. They were disagreeing about what they wanted after.

## Key Takeaways

- **A three-way audience split can resolve to one interface,** if there's a shared first question underneath the disagreement.
- **Explaining jargon and removing jargon are not the same fix.** Keeping precise terms while adding plain-language context beat simplifying the vocabulary.
- **A layered interface is only as good as the sequence it's built on.** Layered disclosure won because it was grounded in real usage, not a basic-versus-advanced guess.
- **Color and type can do functional work.** The semantic system let one screen speak to a store owner and a developer at once.
- **Every metric traced back to sequencing or language,** not a visual refresh.
